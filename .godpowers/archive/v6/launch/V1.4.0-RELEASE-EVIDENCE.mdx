## GitHub release body

```markdown
Voiceprint now cleans copy-and-paste Unicode artifacts before its one
humanizer rewrite while keeping the submitted `Before` text byte-for-byte
intact.

### Added

- A dependency-free, offline text-hygiene helper with importable inspection
  and cleanup APIs plus `inspect` and `clean` CLI operations.
- Deterministic manifests for removed, normalized, and deliberately preserved
  Unicode characters, including code points, names, counts, actions, offsets,
  and preservation reasons.
- Exact fixtures for hidden controls, Unicode spaces, multilingual joiners,
  variation selectors, emoji ZWJ pairs, file safety, size limits, and CLI
  behavior.

### Preserved contracts

- `Before` remains byte-for-byte identical to the submitted text and is still
  diagnosed before cleanup.
- Voiceprint still performs exactly one hygiene cleanup, one humanizer
  invocation, and one report-only residual diagnosis. The residual never
  drives another rewrite.
- The result still has six top-level sections. Hygiene details remain inside
  `What changed`.
- Valid script and emoji sequences, fullwidth letters, confusable visible
  letters, tabs, and line breaks remain protected by the conservative policy.

### Safety and compatibility

- Python 3.10 or newer is required for the local helper. No package, service,
  network connection, or runtime dependency was added.
- Input is limited to 4 MiB. File paths must resolve to unchanged regular,
  non-symbolic-link files. The helper never rewrites a source file in place.
- Hygiene reports observable Unicode actions only. It does not claim
  watermark discovery, provenance attribution, detector-signal removal, or a
  promise about any external detector.

### Verification

- 36 routine tests passed, with the opt-in release benchmark separated from
  ordinary CI as designed.
- The 100,000-code-point release benchmark passed at p95 74.7 ms against the
  200 ms limit on the release-preparation machine.
- Independent hardening completed with zero open Critical, High, Medium, or
  Low findings.

No migration is required. Existing Voiceprint invocations keep the same
entry point and six-section result contract.

**Full diff**: https://github.com/hannsxpeter/voiceprint/compare/v1.3.0...v1.4.0
```

## Success criteria

The release is successful when all of the following are true:

- The public GitHub release is non-draft, not a prerelease, and its tag points to the intended release commit.
- A clean checkout of `v1.4.0` passes the routine test suite, syntax check, eval JSON parse, vendor-header check, and focused standard-input smoke.
- The published skill metadata and README badge both report `1.4.0`.
- The changelog contains the dated `1.4.0` entry and retains an `Unreleased` heading.
- No regression changes `Before`, adds another transformation or diagnosis pass, introduces a runtime dependency or network call, or edits a user source file in place.
- No release-blocking issue is reported during D+1 through D+7 follow-up.

## Rollback

Rollback triggers:

- Any submitted `Before` byte changes.
- More or fewer than one before diagnosis, one cleanup, one humanizer invocation, or one residual diagnosis.
- Any source-file overwrite, path-boundary disclosure, blocking special-file read, network call, or unbounded input behavior.
- Any deterministic fixture mismatch or release benchmark above 200 ms p95 on the designated reference runner.

User rollback is immediate and data-free: pin or check out `v1.3.0`. There is no schema, service, state migration, or stored data to reverse.

Maintainer rollback after publication:

1. Keep the immutable `v1.4.0` tag and release available as historical evidence. Do not retarget the tag.
2. Mark the GitHub release description with a concise known-issue notice if users must stop adopting it.
3. Create a hotfix branch from current `main` and revert merge commit `ab0e448` with mainline parent 1.
4. Update public version references and the changelog for a `v1.4.1` rollback release.
5. Run the full release smoke set and hardening gate again, then create a fresh hash-bound prepublication record before publishing `v1.4.1`.
6. Tell affected users to pin `v1.3.0` until `v1.4.1` is available.
